# card-evaluation — 分開驗證效果、構築價值與遊玩感受

[遊戲開發](README.md)｜[卡牌設計](card-design.md)｜[驗收分流](validation.md)｜[核實筆記](../../../analysis/slay-the-robot/design/cards.md)

**何時用**：評量單卡、升級、牌組原型、協同或改版前後表現，決定保留、調整、移除或再試。

**何時不用**：只查 schema 接 card-design；原語有錯先接 [mechanics](mechanics.md)；只因 smoke 通過便要求「證明平衡」，必須先建立本流程的比較情境。本流程不提供現成自動玩家。

## Done when

存在評量規格、原始試驗紀錄及結論報告；規格列出對照、seed／抽樣、決策策略、指標與事先設定的判定門檻，紀錄填有實際樣本量、失敗／逾時及證據位置。報告分開列功能正確性、目前樣本支持的表現、未完成的人工體驗，並附下一個具體決策。已實作測試有命令及退出結果；工作流 strict lint 回傳 0。

## 流程

### 盤點現有能力，再選問題

2026-10-19 靜態查核基準為 `4dac5abe0d19382f8ace2cec5ed3fd77e2a0e11d` 加本地修復；來源與限制見核實筆記。現有 [combat_flow.gd](../../../tests/combat_flow.gd)／[fixture](../../../tests/combat_fixture.gd) 是受控單場勝敗回歸，[save_load_flow.gd](../../../tests/save_load_flow.gd) 驗跨程序續玩；都不是跨卡池自動策略、勝率模擬器或平衡判分器。不要把固定獲勝劇本反覆執行當作樣本。

先寫可否證問題，例如「在指定牌組與遭遇中，替換一張同費卡後，是否增加擊殺前承傷且沒有增加選擇空間？」選當前產品設計中的對照；框架的測試卡數值只供技術示例，不當成平衡黃金標準。卡牌用途、角色階段與抽樣單位未明時先完成 brief，可先做功能正確性，不能先給全局強弱排名。

試驗欄位與量測定義已抽到 [card-evaluation-fields.json](card-evaluation-fields.json)（11 列）。`id` 是記錄區塊，`record` 是輸入／結果欄位，`measure` 是計算或觀察方式，`limit` 是限制；全部為**建議的試驗契約**，不表示現有 runner 已自動蒐集。任務資料另存 wf-table/1；原始逐步日誌可放 artifacts，持久結論應保留版本、樣本與證據路徑。

### 第一層：先排除規則錯誤

用最小狀態測基礎／升級效果、費用／能量、目標、順序、合法／拒絕、出牌去向和回合觸發。透過真實出牌路徑檢查扣費與 validator；直接呼叫 action 只能作局部效果測試。涉及預覽，重複預覽前後比 RNG、狀態充能與牌堆，確認沒有遊戲副作用。保存回讀只在卡牌永久狀態受影響時加測。

安排可區分錯誤的邊界：剩餘生命恰好擊殺、已有格擋、多段與單段加成、目標先死、手牌上限、空抽牌堆／洗回、沒有可選卡，以及升級超過上限。生成新卡、複製、自動出牌不一定沿用手動出牌費用與 validator；依實際使用路徑分開驗。實際影響功能才補測，無須為每張純數值卡鏡像重寫所有框架測試。

錯誤先修再評量，否則「弱卡」可能只是 action 參數遮住升級、池未接通或順序相反。若疑似既有缺陷不在當次授權內，報告先標阻斷／不納入該比較，不悄悄把故障卡當零收益樣本。

### 第二層：把卡放回牌組與遭遇

每次比較至少固定牌組多重集合、升級、遺物、初始 HP／能量、難度與敵人狀態。選與設計問題相關的單體、多目標、快攻壓力、長戰、減益／反制情境；這是建議測試設計，具體敵人必須從已存在的 ID 或另行授權的 fixture 取得。比較同張替換、加入一張、移除一張與獎勵跳過時，標清是哪種干預，別混用其分母。

冷接手可先查 [現有遭遇](../../../analysis/slay-the-robot/design/cards.md#評量情境的現成入口)：`event_act_1_easy_combat_2` 是單一 enemy_3，但有死亡效果；`event_act_1_easy_combat_3` 是 enemy_1／enemy_2，其中有首傷免疫；`event_act_1_easy_combat_4` 有易傷、連擊及格擋循環。它們是可定位的比較起點，不能代表所有遭遇，也不能把名稱 easy 當強度證據。先按 brief 選情境，再以相同版本的實際敵人資料固定期望。

以無協同、預期協同、低頻／過度協同牌組測卡的角色。紀錄牌何時抽到、可否使用、為何不用、支付後實際完成的效果；抽到太晚與支付不起是構築結果，不能全算成卡片原語失敗。估量循環應看手牌、牌堆、能量與狀態的逐步變化；設定回合／action 上限，達上限列為逾時／疑似循環，保留最小重現，不能算勝或靜默丟棄。

評價稀有度與取得頻率，另跑實際卡包／獎勵路徑抽樣；記錄保底初始狀態、draft 類型、每次候選及選擇。空 bucket、不足張數、未曝光都各有分母。玩家選取率分母是「有提供該卡且有實際選擇」，不能使用所有戰鬥；觀察到選取率也受玩家偏好與選擇策略影響。

### 第三層：讓試驗可以重現與解讀

每批先固定基準與候選版本、內容 hash／mod 次序、引擎、scenario、種子清單、RNG 初始狀態與選牌／出牌策略。定向回歸 seed 用於重現錯誤；代表性評量另用預先保留的 seed 集，避免調參只贏測試 seed。可先用小批確認工具，再按所需精度決定正式樣本量與停止規則；小批結果只列探索性。

對照與候選使用同組 seed 及同一策略，按 seed 配對計算差異。改動抽牌、目標或隨機呼叫次數後，命名 RNG 流可能分岔；同 seed 不保證兩版遭遇完全相同，需留 trace 辨認。重跑同 seed、同操作的確定結果不是新的獨立樣本；同一 run 內多場也不能假設互相獨立。

勝敗報實際勝場／有效場次、未完成數和比例的信賴區間；承傷、回合與收益報分布及配對差異，必要時按 run／seed 分群估區間。先指定區間方法與可信度，採經驗證的統計實作；不能只看平均或單次最高值。多卡多場景探索須揭露比較數，保留額外 seed 驗證選中的改動，避免把碰巧改善當成普遍結論。沒有足夠樣本就寫「證據不足」，不把未顯著差異說成等效。

目前沒有通用對戰策略、批次 balance runner、自動 telemetry 或信賴區間工具。需要大量抽樣時先建立能產出上述紀錄的最小工具，驗證其策略合法、timeout 不吞樣本、結果可重播；不得虛構指令。本次只準備流程，不預先新增模擬器或 MCP。所有實跑由指定 runtime owner 依 [validation](validation.md) 串行安排隔離背景檢查。

### 最後區分可量測表現與體驗

功能通過不等於平衡，某策略勝率提高也不等於玩家更好玩。人工評價需寫參與者／日期／情境與原話或觀察，查看選擇是否可理解、回報是否可預期、等待是否過長、強勢循環是否單調、失敗是否能學到原因。AI 可提出假說與反例，不可冒充實際遊玩者。現行禁止桌面、視窗及 GUI 操作，因此本輪只能規劃這部分，標為尚未驗證。

## 交接

結論採「保留／調整哪個參數或取得方式／再補哪個情境」，附支撐樣本與反例，不只留總分。要改卡回 card-design，要新增機制回 mechanics；與敵人／關卡互動的發現交相應 owner，避免單方修改難度。同步可重複經驗至流程與核實筆記，數值實驗結果留在任務報告，不把某次勝率永久寫成框架規則。
